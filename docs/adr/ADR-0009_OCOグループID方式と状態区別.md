# ADR-0009: OCO はグループID方式とし、CANCELLED（OCO起因）と EXPIRED（建玉消滅）を区別する

- **ステータス**: 採用
- **日付**: 2026-06-28
- **関連**: 指示書「決済注文 B OCO」/ ADR-0008 / ADR-0010(IFOで再利用)

## 背景（なぜ判断が必要だったか）
OCO(TPとSLのセット・片方約定で他方を自動取消)を導入するにあたり、
(1) グループをどう表現するか、(2) 「他方が消える理由」をどう表すか、(3) 部分操作を許すか、を決める必要があった。

## 決定（何を選んだか）
1. **グループID方式**: EXIT注文に `ocoGroupId`(nullable)を1つ持たせ、同一IDのTPとSLが連動する。
   OCO親エンティティは作らない。グループは最大2本(TP×1+SL×1)。
2. **消える理由を区別**: OCOの片方約定による他方の取消は **CANCELLED**、
   対象建玉の消滅による失効は **EXPIRED**(ADR-0008)。新しい状態は増やさない。
3. **セット取消のみ**: OCOのユーザー取消はグループ単位(TP/SL両方)。片方だけの取消は不可。

## 理由（なぜそれを選んだか）
- グループID方式はカラム1つの追加で済み、段階A(単独TP/SL)の構造を崩さない。
  最大2本と決まっているため親エンティティを立てるほどの管理は不要。
- CANCELLED/EXPIREDの区別により、履歴から「利確が刺さって取り消された(狙い通り)」のか
  「ロスカット等で建玉ごと消えた(想定外)」のかが判別でき、学習用途で意味が大きい。
- セット取消のみとすることで「OCOはセットとして意味を持つ」という一貫した思想を保つ
  (この思想は ADR-0010 のIFO失効判断にも波及)。

## 検討した代替案
- **OCO親エンティティ方式** — グループ状態を親が持てるが、エンティティが増え階層が乗る。2本固定には過剰。
- **相互参照方式**(TPとSLが互いのIDを指す) — シンプルだが拡張性が低い。
- **消える理由を区別しない(両方EXPIRED)** — シンプルだが履歴の意味が失われる。
- **片方だけの取消を許す** — OCOが途中で単独TP/SLに変質し、グループの扱いが複雑化。将来必要なら緩める。

## 結果（トレードオフ・影響）
- 片方約定→対象建玉決済→他方CANCELLED は口座ロック内で一括実行(分断させない)。
- `ocoGroupId` の仕組みは段階C(IFO)でそのまま再利用され、追加フィールドなしでIFOが成立した。
- 状態色の使い分け(取消=ミュート/失効=警告色)を DESIGN.md に反映。
