# DemoFX 機能指示書: 決済注文 段階C-1（IFD・新規＋決済1本の合成注文）

## 1. 準拠
- 実装ルールは **CODEX.md** に従う(BigDecimal/HALF_UP、DTO返却、独立スケジュール、口座ロックで直列化、
  既存を壊さない・小ステップ、NEXT_PUBLIC_API_BASE_URL、logs非Git、着手前に既存を調査・報告)。
- UIは **DESIGN.md** に従う(注文パネル、待機注文/予約一覧、PositionsTable、状態の色分け)。
- 設計の正: **「決済注文 TP/SL → OCO → IFD/IFO 設計全体像」**(本書は段階C のうち **IFD**)。
- 前提機能: 指値・逆指値(新規エントリー)、段階A(単独TP/SL・建玉紐づけ・EXPIRED失効)。
  ※ IFO(新規＋OCO)は段階B(OCO)を内包するため、**本書の後(C-2)** とする。

## 2. ゴール / 位置づけ
- **IFD(If Done)** = 新規注文(指値/逆指値)＋決済レッグ1本(TP または SL)の合成注文。
- 「この価格で新規エントリーできたら、約定したら自動でTP(またはSL)を仕掛ける」を1セットで予約できる。
- 段階の位置づけ: A(単独TP/SL)→ B(OCO)→ **C-1 IFD(本書)**→ C-2 IFO(新規＋OCO)。

## 3. スコープ
### スコープ内
- IFD の発注・取消・一覧(親=新規注文＋子=決済レッグ1本)
- 親が約定 → 建玉生成 → **子を建玉にバインドして有効化(PENDING化)**
- 約定時の子の**向き検証**と、不正時は**子だけEXPIRED**(新規約定は成立)
- 親が約定前に取消 → **子も一緒に消す**
- バインド後の決済挙動は**段階Aを再利用**

### スコープ外(後続 / 別)
- **IFO(新規＋OCO)** = C-2(段階BのOCOを内包)
- 部分決済(全数量決済のみ)、許容スリッページ幅指定

## 4. 設計概要
### 4.1 親子モデル
- **親** = 新規注文(既存の指値・逆指値 = TriggerOrder, purpose=ENTRY)。
- **子** = 決済レッグ1本(TP=決済指値 or SL=決済逆指値, purpose=EXIT)。
  - 子は発注時には**対象建玉が未確定**(親がまだ約定していない)。**待機・未バインド**の状態で保持する。
  - 親子の関連: 子が親の注文IDを参照(`parentOrderId`)。
- IFD は子が**1本**(TP か SL のどちらか)。OCO(2本)は IFO(C-2)。

### 4.2 状態遷移
```
親(新規): PENDING --約定--> 建玉生成 ──┐
                                        ├─→ 子を建玉にバインドして有効化(子: PENDING)
子(決済): 待機(未バインド) ─────────────┘
親(新規): PENDING --取消--> 子も CANCELLED(まだ建玉が無いので決済レッグも消す)
```
- バインド後、子は段階Aの単独TP/SLと同じライフサイクル(発動TRIGGERED / 取消CANCELLED / 失効EXPIRED)。

### 4.3 価格向き検証(2段構え・最終判定は約定時)
- **発注時**: 軽い妥当性チェックのみ(数量>0、価格>0、ペア有効、親注文の向き検証=既存)。
  子のTP/SLの向きは、この時点では**確定的に判定しない**(約定時に価格が動くため)。
- **約定時(最終判定)**: 親が約定して建玉ができた時点の価格で、子のTP/SLの**向きを判定**:
  - LONG: TP は建玉時Bidより上 / SL は建玉時Bidより下。
  - SHORT: TP は建玉時Askより下 / SL は建玉時Askより上。
  - **向きが正当** → 子を建玉にバインドして有効化(PENDING)。
  - **向きが不正**(相場が動きすぎて成立不能) → **新規約定は成立させ、子だけ EXPIRED**(失効)。
    建玉は通常どおり保持され、ユーザーは改めて決済注文を出せる。

### 4.4 約定時の決済価格(段階A踏襲)
- バインド後の発動時: 利確(TP)=指定価格で約定 / 損切り(SL)=トリガー後の現在値で約定(スリッページ幅指定なし)。

## 5. バックエンド仕様
### 5.1 既存調査(着手前に view して報告)
- 指値・逆指値(新規)の発注・監視・約定→建玉生成、段階AのEXIT注文/バインド/失効、口座ロックの所在。
  親約定時に子をバインドする差し込み点を報告。

### 5.2 enum / フィールド(additive)
- 子(EXIT注文)に **`parentOrderId`(nullable)** を追加(IFDの親=新規注文を指す)。
- 子の未バインド状態を表せるようにする(例: 既存statusに **PENDING(未バインド)** を流用しつつ、
  `targetPositionId` が未設定=未バインドとして扱う / もしくは状態 **WAITING_PARENT** を追加)。
  - どちらにするかは既存構造に合わせて判断・報告(最小追加)。
- 既存 TriggerStatus(PENDING/TRIGGERED/CANCELLED/REJECTED/EXPIRED)を流用。

### 5.3 サービス
- IFD発注: 親(新規指値/逆指値)＋子(TP or SL)を**1リクエスト**で受け、親子を関連づけて登録。
  - 親は既存の新規指値・逆指値の登録経路を再利用。子は未バインドで保持。
- 親約定フック(既存の新規トリガー発動に差し込む):
  1. 親が約定 → 建玉生成(既存)。
  2. 子の**向きを約定時価格で判定**(4.3)。
  3. 正当 → 子の `targetPositionId` に建玉をセットしてバインド・有効化(PENDING)。
  4. 不正 → 子を **EXPIRED**(新規約定はそのまま成立)。
- 親取消: 親がPENDINGのうちに取消 → 子も **CANCELLED**(建玉が無いので決済レッグも消す)。
- バインド後の子は段階Aの監視・決済・失効をそのまま利用(新規ロジックを作らない)。
- 口座ロックで直列化・冪等。

### 5.4 API
- `POST /api/trade/orders/ifd`: IFD発注
  ```
  {
    "entry": { "currencyPair":"USD/JPY","side":"BUY","orderType":"LIMIT","quantity":10000,"triggerPrice":154.500 },
    "exit":  { "type":"TP","triggerPrice":156.000 }     // type は TP または SL の1本
  }
  ```
  - 親の向き検証(既存)に反したら却下。子は軽い妥当性のみ(数量/価格/型)。
- `POST /api/trade/orders/pending/{id}/cancel`(既存を流用 or IFD用):
  親(PENDING)取消で子も CANCELLED。
- `GET /api/trade/orders/pending`(拡張): IFD の親子関係(子の未バインド状態)を表示できるようにする。
- DTO返却。

### 5.5 エッジケース
| ケース | 期待挙動 |
|---|---|
| 親約定・子の向き正当 | 子を建玉にバインドして有効化(PENDING) |
| 親約定・子の向き不正(相場が動きすぎ) | 新規約定は成立、子だけ EXPIRED |
| 親が約定前に取消 | 子も CANCELLED(建玉は無い) |
| 親約定時に余力不足 | 既存の新規約定の余力チェックに従う(約定しなければ子も CANCELLED) |
| バインド後に建玉が他経路で消滅 | 子は EXPIRED(段階A) |
| 同時操作・二重発動 | 口座ロックで直列化・冪等 |

## 6. フロントエンド仕様
- **注文パネル**に IFD 入力を追加:
  - 新規条件(成行は対象外。指値/逆指値＋数量＋トリガー価格)＋ 決済レッグ1本(TP or SL の価格)。
  - 子の価格は「約定時に向きを判定」する旨をヒント表示(発注時点では厳密拒否しない)。
- **待機注文パネル**に IFD の親子関係を表示(親=新規待機、子=未バインド/バインド済み)。
- 親約定で子が建玉にバインドされ、PositionsTable に TP/SL が出るのが見える。
- 子が約定時に失効した場合は EXPIRED として表示(建玉は残る)。
- 状態の色分け(待機/未バインド/発動/取消/失効)は DESIGN.md。loading/empty/error。

## 7. この機能固有の制約
- IFD の子は **1本**(TP か SL)。OCO(2本)は IFO(C-2)。
- 子の向きの**最終判定は約定時価格**。発注時は軽い妥当性のみ。
- 約定時に子が不正 → **新規約定は成立・子だけ EXPIRED**(ロールバックしない)。
- 親が約定前に取消 → 子も CANCELLED。
- バインド後は段階A(単独TP/SL)を再利用(全数量決済・決済価格方式・建玉消滅失効はAに準拠)。

## 8. 実装ステップ
1. 既存調査: 新規指値・逆指値の約定→建玉生成、段階Aのバインド/失効、ロックの差し込み点を報告。
2. 子に `parentOrderId` と未バインド表現を追加(最小)。
3. IFD発注サービス(親＋子1本を関連づけて登録、子は未バインド)。
4. 親約定フック: 約定時価格で子の向き判定 → 正当=バインド有効化 / 不正=子EXPIRED(新規は成立)。
5. 親取消で子もCANCELLED。
6. API(ifd発注 / 取消 / pending拡張)を追加。
7. テスト追加(9章)。
8. フロント: 注文パネルのIFD入力、待機注文の親子表示。
9. 動作確認(10章)。

## 9. テスト（受け入れ条件）
- **IFD発注**: 新規指値＋TP を1リクエストで発注 → 親PENDING、子は未バインドで保持。
- **親約定→子バインド**: 親約定で建玉生成 → 子(TP)が建玉にバインドされ PENDING、PositionsTable にTP表示。
- **子の向き不正で失効**: 約定時に相場が動き子の向きが不正 → 新規約定は成立(建玉あり)、子は EXPIRED。
- **親約定前の取消**: 親をPENDINGで取消 → 子も CANCELLED(建玉なし)。
- **バインド後の発動**: バインドされたTPが価格到達 → 指定価格で決済・建玉CLOSED(段階A挙動)。
- **冪等/直列化**: 同時約定・操作で二重バインド・二重決済しない。

### バックエンド
```

POST /api/trade/orders/ifd {

  "exit":  { "type":"TP","triggerPrice":156.000 }

# ニュース等で下落させ親を約定させる

GET  /api/trade/positions           # 建玉CLOSED
GET  /api/trade/trades              # 決済約定
```

- 親を約定前に取り消すと子も消える。既存画面が壊れていない。
