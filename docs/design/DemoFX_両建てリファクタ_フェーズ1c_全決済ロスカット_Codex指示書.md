# DemoFX 機能指示書: 両建てリファクタ フェーズ1c（全決済ロスカットの建玉ベース化）

## 1. 準拠
- 実装ルールは **CODEX.md** に従う(BigDecimal/HALF_UP、DTO返却、独立スケジュール、口座ロックで直列化、
  既存を壊さない・小ステップ、NEXT_PUBLIC_API_BASE_URL、logs非Git、着手前に既存を調査・報告)。
- UIは **DESIGN.md** に従う(AlertPanel、MarginGauge、状態配色 SAFE/WARNING/DANGER)。
- 前提機能: 1a(個別建玉・個別決済)、1b(建玉ベースの含み損益・必要証拠金SUM・維持率)、
  既存④bのロスカット監視・アラート(LOSS_CUT/MARGIN_WARNING)。
- 関連設計メモ: 「両建てリファクタ 設計メモ」6章(ロスカット)を正とする。本書はフェーズ1の **1c**。

## 2. ゴール / 位置づけ
- ロスカットを**建玉ベース**に対応させ、発動水準を超えたら **全OPEN建玉を一括成行決済(全決済)** する。
  - 両建て中(LONG/SHORT共存)でも、**LONG・SHORT 問わず全建玉を閉じてフラット**にする。
- これでフェーズ1(個別建玉モデル＋HEDGING＋証拠金SUM/レートFIXED＋全決済ロスカット)が完成する。
- フェーズ1の位置づけ: 1a(建玉モデル)→ 1b(評価)→ **1c(全決済ロスカット・本書)**。

## 3. スコープ
### スコープ内
- ロスカット監視を 1b の建玉ベース維持率に接続
- 発動時に**全OPEN建玉を成行で一括クローズ**(1aのクローズ経路を再利用)
- 実現損益確定 → 残高反映 → 全建玉フラット
- LOSS_CUT アラート(既存④bのアラートを建玉ベースに合わせて発生)

### スコープ外(後続)
- **段階的清算**(維持率回復まで含み損の大きい順に1建玉ずつ決済)＝将来の学習トピック
- 部分決済、決済行(TP/SL)、NETTINGモード(フェーズ2)、MAX/REVALUEポリシー
- 発動水準そのものの変更(既存設定を踏襲)

## 4. 設計概要
### 4.1 監視と発動(④b踏襲・建玉ベース化)
- 既存④bの独立スケジュール監視を踏襲し、**1bの建玉ベース維持率**を参照する。
- 判定(④b同様):
  - 維持率が **null**(建玉なし/レート欠落)→ 何もしない(誤発動防止)。
  - 維持率 ≤ ロスカット閾値(既存設定、既定50%)→ ロスカット発動。
  - warning域 → MARGIN_WARNING、回復で解消(既存踏襲)。

### 4.2 全決済の実行
- 口座ロックを取得 → OPEN建玉を再取得・維持率を再計算 → まだ閾値以下なら全決済。
- **全OPEN建玉(LONG/SHORT問わず)を成行で一括クローズ**:
  - 各建玉を 1a の個別決済経路でクローズ(LONG→Bid / SHORT→Ask)。建玉IDごとに回す。
  - 実現損益を確定し残高へ反映。全建玉が CLOSED → フラット。
- 強制決済の約定には由来が分かる印(source=LOSS_CUT 等、既存④bの方針を踏襲)。
- 冪等: ロック内で状態確認し、二重発動・二重決済しない。決済後は維持率=null となり再発動しない。

## 5. バックエンド仕様
### 5.1 既存調査(着手前に view して報告)
- 既存④bのロスカット監視(スケジュール・口座ロック・LOSS_CUTアラート発生箇所)、
  1aの個別決済経路(closePosition)、1bの建玉ベース維持率算出の接続点を報告。

### 5.2 サービス
- ロスカット監視(④b)を改修:
  - 維持率の取得を 1b の建玉ベース算出に向ける。
  - 発動時の処理を「全OPEN建玉を 1a のクローズ経路で一括決済」に置き換える。
  - 口座ロックは既存を共用(発注・個別決済・トリガー発動・ロスカットを直列化)。
- LOSS_CUT アラート: 発動時に発生(メッセージに維持率・決済建玉数等)。warning/回復の扱いは既存踏襲。

### 5.3 API
- 専用APIは不要(内部実行)。結果は既存の建玉一覧・約定履歴・口座サマリ・アラートに反映。

### 5.4 エッジケース
| ケース | 期待挙動 |
|---|---|
| 維持率 null(建玉なし/レート欠落) | 発動しない |
| 両建て共存中の発動 | LONG/SHORT 問わず全OPEN建玉を閉じてフラット |
| 一部ペアのレート欠落 | そのペアを閉じられない場合の扱いを明示(閉じられる分は閉じ、再評価で継続/ログ) |
| 同時操作(発注・個別決済とロスカット) | 口座ロックで直列化、冪等 |
| 発動後 | 全建玉フラット→維持率null→再発動しない |

## 6. フロントエンド仕様
- 専用の新規UIは基本不要(1a/1b/④bで配線済み)。動作として:
  - 維持率が閾値以下になると**全建玉が消えてフラット**になり、PositionsTable が空に。
  - AlertPanel に **LOSS_CUT**(CRITICAL)が出る。MarginGauge は建玉なしで維持率「—」に戻る。
- loading/empty/error は既存踏襲。DESIGN.md の配色に従う。

## 7. この機能固有の制約
- ロスカットは**全決済**(全OPEN建玉一括)。両建て分も含めて閉じる。段階的清算はしない(将来トピック)。
- 発動水準は**既存設定を踏襲**(変更しない)。
- 維持率 null では発動しない。口座ロックで直列化し冪等に作る。

## 8. 実装ステップ
1. 既存調査: ④bロスカット監視・1aクローズ経路・1b維持率算出の接続点を報告。
2. 監視の維持率取得を 1b 建玉ベースに接続。
3. 発動時処理を「全OPEN建玉を 1a クローズ経路で一括決済」に置き換え(ロック・冪等)。
4. LOSS_CUT アラート発生を建玉ベースに合わせる(warning/回復は既存踏襲)。
5. テスト追加(9章)。
6. フロント動作確認(専用UIは原則不要)。
7. 動作確認(10章)。

## 9. テスト（受け入れ条件）
- **全決済発動**: 維持率 ≤ 50% を作る → 全OPEN建玉が一括成行決済され、フラットになる。
- **両建ても全決済**: LONG/SHORT 共存状態でも、発動で両方とも閉じてフラット。
- **実現損益反映**: 強制決済の実現損益が残高に反映され、約定履歴に source=LOSS_CUT で残る。
- **アラート**: LOSS_CUT(CRITICAL)が発生する。
- **null安全**: 建玉なし/維持率算出不能では発動しない。
- **冪等**: 一度の発動で二重決済しない。決済後は再発動しない。

## 10. 動作確認手順
### バックエンド
```
# 大きめの両建て/建玉を作る(1a)
POST /api/trade/orders/market { "currencyPair":"USD/JPY","side":"BUY","quantity":100000 }

# 含み損で維持率を落とす(③ニュースイベントで逆行)
POST /api/market/news/events { "currencyPair":"USD/JPY","direction":"DOWN","magnitudeBps":300,"durationSeconds":60 }

# 維持率低下 → 全決済ロスカット発動を確認
GET /api/trade/account/summary
GET /api/trade/positions                      # 全OPEN建玉が消えてフラット
GET /api/market/alerts?activeOnly=false       # LOSS_CUT が出る
GET /api/trade/trades                          # 強制決済が source=LOSS_CUT で記録
```
### フロントエンド
- ニュースで逆行 → 維持率が下がり、閾値割れで全建玉(両建て含む)が消えてフラット、AlertPanel に LOSS_CUT。
- 既存画面(1a建玉複数行・個別決済、1b評価・証拠金/維持率、監視・成行・指値/逆指値)が壊れていない。
