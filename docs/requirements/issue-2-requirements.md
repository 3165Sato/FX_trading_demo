# 要件ドラフト

## 背景

GitHub Issue #2「Claude Code - Codex連携のテストIssue」では、注文を取り消して再発注する手間を省く実務機能として「注文変更（訂正）」が求められている。また、変更履歴の扱いを学べる機能と位置付けられている。

現行システムには、指値・逆指値の新規予約注文、建玉に対する単独 TP/SL、OCO、IFD、IFO、およびそれらの取消・自動発動が実装されているが、待機中注文の価格または数量を訂正する操作は確認できなかった。

## 目的

未発動の予約注文および TP/SL を、取消と再発注に分けずに訂正できるようにする。

最低限、訂正可能条件、入力値検証、監視処理との整合性、複合注文への影響、および変更履歴の扱いを明確にし、安全に実装・テストできる要件を定める。

## 現状仕様

- 新規の予約注文は `POST /api/trade/orders/pending` で登録する。
- 予約注文の入力は通貨ペア、売買区分、注文種別（LIMIT/STOP）、数量、トリガー価格である。
- 単独 TP/SL は `POST /api/trade/positions/{id}/exit-orders` で登録する。
- 単独 TP/SL の入力は種別（TP/SL）とトリガー価格だけであり、数量は対象建玉の数量から設定される。
- OCO は `POST /api/trade/positions/{id}/oco-orders` で TP/SL の価格を登録し、2 本に同一の `ocoGroupId` を設定する。数量は対象建玉の数量から設定される。
- IFD/IFO の子 TP/SL は親注文の数量を引き継いで未紐付け状態で作成され、親約定後に生成された建玉へ紐付けられる。その際、子注文の数量は生成された建玉の数量で再設定される。
- 未発動として扱われる内部状態は `PENDING` と `WAITING` である。監視処理は両状態の注文 ID を取得し、既定で 1 秒間隔に評価する。
- 予約注文は `POST /api/trade/orders/pending/{id}/cancel` で取り消せる。ただし OCO の注文は単体で取り消せない。
- 単独 TP/SL は `DELETE /api/trade/positions/{id}/exit-orders/{exitId}`、OCO は `DELETE /api/trade/positions/{id}/oco-orders/{groupId}` で取り消せる。
- 新規予約注文の価格は、現在の約定側価格（BUY は Ask、SELL は Bid）との方向関係を検証する。
- TP/SL の価格は、建玉の決済側価格（LONG は Bid、SHORT は Ask）との方向関係を検証する。
- 価格は通貨ペアの `priceScale`、数量は `quantityScale` に従い `HALF_UP` で丸める。
- フロントエンドの Pending orders パネルは未発動注文の通貨ペア、種別、売買区分、価格と Cancel 操作を表示する。数量表示および Edit 操作はない。
- 建玉詳細では TP/SL/OCO の新規登録と取消を行えるが、訂正操作はない。
- `trigger_orders` には数量とトリガー価格が保存されるが、訂正履歴専用のエンティティまたは項目は確認できなかった。

## 変更後仕様

- ユーザーは、未発動の通常予約注文について、トリガー価格および数量を訂正できること。
- ユーザーは、未発動の TP/SL について、少なくともトリガー価格を訂正できること。
- Issue に記載された TP/SL の「数量変更」は対象範囲とするが、現行の建玉全数量決済との整合ルールが確定するまで詳細仕様を確定しない。
- 訂正は対象注文が未発動であることをサーバー側で再確認してから反映すること。
- 訂正値には、新規登録時と同等の必須、正数、桁数・丸め、および現在レートに対する価格方向の検証を適用すること。
- 対象注文の通貨ペア、売買区分、注文種別、目的（ENTRY/EXIT）、対象建玉、親注文、および OCO グループとの関係は、価格・数量の訂正によって意図せず変更されないこと。
- 発動済み、取消済み、拒否済み、失効済みの注文は訂正できないこと。
- 訂正処理と監視・約定処理が競合した場合、訂正と発動が部分的または二重に成立しないこと。
- 訂正処理は、既存のトリガー発動、TP/SL 登録・取消、OCO 操作と同じデモ口座単位の `AccountTradeLockService` 内で実行し、トランザクション内で対象注文を再取得して状態を検証すること。
- 訂正 API は部分更新を表す `PATCH` を使用し、通常予約注文は既存の注文リソース配下、建玉に紐づく TP/SL は既存の建玉・決済注文リソース配下に配置すること。具体的な OCO/IFD/IFO 用 API は、各注文の訂正単位が確定してから定めること。
- 訂正対象として変更できる属性はトリガー価格と数量だけとし、通貨ペア、売買区分、注文種別、目的、TP/SL 種別および関連 ID は変更不可とすること。
- OCO の訂正単位および IFD/IFO の親子数量連動は、確定したルールに基づき一貫して処理すること。
- 成功時には、訂正後の注文情報を返し、画面上の Pending orders または建玉詳細に反映すること。
- 成功応答は Entity ではなく既存の `PendingOrderResponse` または `PositionExitOrderResponse` と同系統の DTO とすること。
- 失敗時には、既存値を部分更新せず、`ResponseStatusException` と既存の `ApiErrorResponse(message)` 形式で理由をユーザーに表示できること。
- Issue が背景として挙げる「変更履歴」を保持する場合は、訂正前後の値、対象注文、訂正日時を追跡できること。ただし保持方式と表示要否は未確定とする。

## 対象範囲

- 通常の指値・逆指値予約注文の価格訂正
- 通常の指値・逆指値予約注文の数量訂正
- 単独 TP/SL の価格訂正
- Issue の記載に基づく TP/SL 数量訂正の要件確定
- OCO、IFD、IFO に含まれる未発動注文を訂正した場合の整合ルール
- 訂正用バックエンド API、サービス処理、入力 DTO、永続化処理
- Pending orders および建玉詳細からの訂正操作
- 訂正後表示の再取得・状態反映
- バックエンドおよび必要なフロントエンドの最低限のテスト

## 対象外

- 成行注文の訂正
- すでに発動、約定、取消、拒否、失効した注文の訂正
- 通貨ペア、売買区分、注文種別、TP/SL 種別の変更
- 約定済み取引または建玉の約定価格・履歴の改変
- 注文監視間隔、レートシミュレーター、証拠金・ロスカット計算方式そのものの変更
- 実運用向け認証・権限管理
- 本 Issue で明示されていない高度な注文訂正（有効期限、スリッページ許容幅等）

## 入力

- 訂正対象を一意に識別する注文 ID
- 通常予約注文の場合:
  - 訂正後トリガー価格
  - 訂正後数量
- TP/SL の場合:
  - 訂正後トリガー価格
  - 訂正後数量（許可条件と意味は未確定）
- OCO をグループ単位で訂正する場合:
  - OCO グループ ID
  - TP の訂正後価格
  - SL の訂正後価格
  - 訂正後数量（許可する場合）
- 対象建玉 ID（建玉に紐づく TP/SL の API で必要とするかは API 形式と併せて未確定）
- API リクエストでは訂正後の価格・数量を `BigDecimal` として扱い、通貨ペアの scale に従って正規化する。

## 出力

- 訂正成功時:
  - 訂正後の注文 ID
  - 通貨ペア
  - 売買区分
  - 注文種別
  - 訂正後数量
  - 訂正後トリガー価格
  - 状態
  - ENTRY/EXIT、TP/SL、対象建玉、親注文、OCO グループ等の既存関連情報
- 訂正失敗時:
  - HTTP ステータス
  - ユーザーが原因を識別できるエラーメッセージ
- 変更履歴を提供する場合:
  - 訂正前後の価格・数量
  - 訂正日時
  - 対象注文との関連

## 正常系

- `PENDING` の通常予約注文の価格だけを有効な値へ訂正できる。
- `PENDING` の通常予約注文の数量だけを正数へ訂正できる。
- 価格と数量を同時に訂正できる。
- 訂正値が通貨ペアの scale を超える場合、既存ルールと同じ `HALF_UP` で正規化される。
- 訂正 API が成功した場合、既存のレスポンス DTO と同じ注文識別子・状態・関連情報を含む訂正後スナップショットが返る。
- 訂正後の指値・逆指値価格が現在の Bid/Ask に対して有効な方向であれば保存される。
- 未発動の単独 TP/SL の価格を、対象建玉と現在の決済側価格に対して有効な方向へ訂正できる。
- 訂正後の値が監視処理の次回評価から利用される。
- API 応答および画面再取得で訂正後の値が表示される。
- 複合注文を訂正対象とする場合、確定した親子・OCO ルールに従って関連注文が一貫して更新される。

## 異常系

- 注文 ID が存在しない場合は Not Found 相当とし、更新しない。
- 対象注文が発動済み、取消済み、拒否済み、失効済みの場合は Conflict 相当とし、更新しない。
- 価格または数量が null、非数、0 以下の場合は Bad Request 相当とし、更新しない。
- 訂正後価格が注文種別・売買区分と現在レートの関係に反する場合は Bad Request 相当とし、更新しない。
- TP/SL の訂正後価格が建玉方向と現在の決済側価格の関係に反する場合は Bad Request 相当とし、更新しない。
- TP/SL の対象建玉が存在しない、当該デモ口座に属さない、または OPEN でない場合は更新しない。
- 訂正対象と指定された建玉、親注文または OCO グループの関係が一致しない場合は更新しない。
- OCO の一方だけを変更できない仕様とした場合、単体訂正要求を拒否する。
- 監視処理が先に注文を発動した場合、遅れて到着した訂正を拒否し、発動結果を上書きしない。
- 複数項目または複数レッグのうち一部の検証・保存に失敗した場合、全体をロールバックする。
- 最新市場レートが取得できず価格方向を検証できない場合は更新しない。
- 同じ口座の訂正と発動が競合した場合は口座ロックで直列化し、ロック取得後に再取得した状態が未発動でなければ訂正を拒否する。

## 既存機能への影響

- `TriggerOrderService` の登録・取消・監視・約定処理と同じ注文レコードを更新するため、同時実行制御が必要になる。
- 既存の `AccountTradeLockService` を訂正処理にも適用する。現行の単一デモ口座・単一アプリケーション内の取引直列化方針では、新たな楽観ロック項目を必須としない。
- 監視対象の抽出は `PENDING` と `WAITING` のため、訂正可能状態の定義が監視対象と整合している必要がある。
- 通常予約注文の数量変更は、発動後に `TradeExecutionService` へ渡る発注数量を変える。
- TP/SL の数量変更を許可すると、現行の全数量決済前提、建玉数量、OCO 相互取消、IFD/IFO 子注文の数量引継ぎに影響する。
- OCO は同一グループの最大 2 本を一体として扱う既存 ADR があるため、単体訂正の許否を明確にする必要がある。
- IFD/IFO の親注文数量を変更した場合、未発動の子 TP/SL 数量との同期要否を決める必要がある。
- 変更履歴を永続化する場合、DB スキーマ、取得 API、History 画面の表示対象に影響し得る。
- Pending orders パネルは現在数量列と Edit 操作を持たないため、UI 変更が必要になる。
- 建玉詳細の TP/SL/OCO 操作は現在新規登録と取消のみであり、既存注文を編集状態へ読み込む UI が必要になる。

## 制約事項

- 本アプリは学習用の架空 FX デモであり、実資産・実取引を扱わない。
- 価格・数量・金額は `BigDecimal` を使用し、価格は `priceScale`、数量は `quantityScale`、丸めは `HALF_UP` とする既存方針に従う。
- 約定側価格は BUY が Ask、SELL が Bid、建玉の決済側価格は LONG が Bid、SHORT が Ask である。
- API は Entity を直接返さず DTO を使用する既存方針に従う。
- 訂正 API の失敗応答は既存の `ApiExceptionHandler` が返す `ApiErrorResponse(message)` に従う。
- 設定値を追加する場合は `application.yml` または既存の設定体系に置き、コードへ直書きしない。
- 口座単位の取引ロックおよびトランザクション境界を損なわない。
- 新たな設定値を必要としない限り、注文訂正のためだけの設定項目は追加しない。
- OCO の片側約定時の他方取消、建玉消滅時の TP/SL 失効、IFD/IFO の親子バインドという既存仕様を維持する。
- フロントエンドの API ベース URL は `NEXT_PUBLIC_API_BASE_URL` を使用する。
- 既存 UI の「表は情報表示、操作は詳細パネルへ」という ADR 方針との整合を取る。

## テスト観点

- 通常予約注文の価格のみ、数量のみ、両方の訂正
- 各売買区分と LIMIT/STOP の価格方向境界
- LONG/SHORT と TP/SL の価格方向境界
- 通貨ペア別の価格・数量 scale と `HALF_UP`
- null、0、負数、不正形式、極端に大きい値
- 存在しない注文、対象建玉不一致、口座不一致、OPEN でない建玉
- `PENDING` および、訂正対象に含める場合の `WAITING`
- `TRIGGERED`、`CANCELED`、`CANCELLED`、`REJECTED`、`EXPIRED` の拒否
- 訂正と 1 秒間隔の監視・発動が競合する場合の排他性
- 口座ロック取得後の状態再確認と、未発動でなくなった注文の訂正拒否
- 訂正成功後、監視処理が訂正後価格・数量で発動すること
- OCO の一括訂正、片側だけの要求、片側検証失敗時の全体ロールバック
- IFD/IFO の親数量訂正と子数量の整合
- 親約定前の子 TP/SL 価格訂正と、親約定時の再検証・バインド
- 建玉数量を超える、または建玉数量未満の TP/SL 数量を許可する場合の決済結果
- 訂正履歴を保持する場合、訂正前後値と時刻が欠落せず、業務注文履歴を破壊しないこと
- API 応答 DTO とエラー応答
- UI の入力検証、送信中の二重操作防止、成功後再表示、失敗時の値保持とメッセージ
- 既存の登録、取消、OCO 相互取消、建玉消滅時失効、IFD/IFO バインドの回帰

## 確認できた事実

- Issue #2 のタイトルは「Claude Code - Codex連携のテストIssue」で、2026-07-26 時点で Open、コメントは 0 件である。
- Issue 本文には「待機中の予約注文・TP/SLの価格/数量を変更」と「最低限必要なテスト」が完了条件として記載されている。
- Issue 本文は、変更履歴の扱いを学べることを背景に挙げているが、履歴の保存項目、表示先、保持期間は指定していない。
- 予約注文と TP/SL は `TriggerOrder` エンティティおよび `trigger_orders` テーブルで管理され、数量とトリガー価格を持つ。
- 現行バックエンドには注文訂正用の公開 API またはサービスメソッドがない。
- 現行フロントエンドには注文訂正用の API 関数、状態、ボタン、フォームがない。
- 通常予約注文の新規登録では数量と価格を入力する。
- 単独 TP/SL と OCO の新規登録では価格のみ入力し、数量は対象建玉から自動設定する。
- IFD/IFO の子 TP/SL は親の数量を引き継ぎ、親約定時に生成建玉の数量へ再設定される。
- `PENDING` と `WAITING` は、取消可能状態、監視対象状態、および既存 TP/SL 重複確認上の未発動状態として扱われる。
- 現行の注文関連テストは TP 作成・価格方向拒否・発動、OCO 作成・相互取消、IFD/IFO 作成・親約定時バインドを対象としている。訂正テストはない。
- `demofx.pending-orders.evaluation-interval-seconds` は 1 に設定されている。
- DB スキーマは Spring JPA の `ddl-auto=update` を使用している。
- `gh issue view 2 --comments` は実行環境ポリシーにより拒否されたため、同一リポジトリの GitHub コネクタで Issue のタイトル、本文、状態、コメント一覧を取得した。

## AI判断で確定した事項

### 訂正可能な属性を価格・数量に限定する

- 判断内容: 訂正で変更できる属性はトリガー価格と数量だけとする。通貨ペア、売買区分、注文種別、ENTRY/EXIT、TP/SL 種別、対象建玉 ID、親注文 ID、OCO グループ ID は変更しない。
- 判断理由: Issue の完了条件が価格・数量の変更だけを指定しており、それ以外を変更すると注文の意味や関連構造が変わる。既存機能を壊さず最小追加とするリポジトリ方針にも合致する。
- 根拠: GitHub Issue #2、`CODEX.md`「既存の Entity / Repository / Service / Controller / 画面を壊さない」「足りない項目だけ最小追加」、`TriggerOrder.java`。

### 新規登録時と同じ数値正規化・価格方向検証を適用する

- 判断内容: 訂正後の価格・数量は `BigDecimal` で扱い、`priceScale` / `quantityScale` と `HALF_UP` を適用する。通常予約注文には `validateBasicRequest` と `validateTriggerDirection` 相当、バインド済み TP/SL には `validateExitDirection` 相当の検証を適用する。
- 判断理由: 訂正によって新規登録では作成できない不正注文を作れてはならず、既存の発動処理は保存済みの価格・数量をそのまま利用するためである。
- 根拠: `CODEX.md`「数値・計算」、`TriggerOrderService.java` の `placePendingOrder`、`placeExitOrderLocked`、`validateBasicRequest`、`validateTriggerDirection`、`validateExitDirection`。

### 訂正処理を口座ロック内で直列化する

- 判断内容: 訂正は `@Transactional` とデモ口座単位の `AccountTradeLockService.withAccountLock` の内側で行い、ロック取得後に対象注文を再取得して未発動状態を確認する。現行構成では訂正のためだけに楽観ロック項目を追加しない。
- 判断理由: 予約注文監視も同じ口座ロック内で発動を処理しており、同じロックに参加させれば単一アプリケーション内の訂正と発動を直列化できる。不要な DB 項目追加を避ける既存方針にも合う。
- 根拠: `CODEX.md`「口座のトレード生成は口座ロックで直列化」、`AccountTradeLockService.java`、`TriggerOrderService.java` の `evaluatePendingOrder`、`placeExitOrder`、`placeOcoOrder`、`cancelExitOrder`、`cancelOcoOrder`。

### 訂正 API は PATCH と既存リソース階層を使用する

- 判断内容: 部分更新を表す HTTP `PATCH` を使用する。通常予約注文は `/api/trade/orders/pending/{id}`、建玉に紐づく単独 TP/SL は `/api/trade/positions/{positionId}/exit-orders/{exitOrderId}` の既存リソース階層に置く。OCO/IFD/IFO の具体的な API は訂正単位の人間判断後に確定する。
- 判断理由: 既存の登録・取得・取消 URL と同じリソース階層を維持でき、価格または数量の部分更新という操作の意味を HTTP メソッドで明示できる。
- 根拠: `TradeController.java`、`PositionController.java` の既存 URL、`PendingOrderRequest.java`、`PositionExitOrderRequest.java`。

### DTO と既存エラー形式を維持する

- 判断内容: 成功時は既存の `PendingOrderResponse` / `PositionExitOrderResponse` と同系統の DTO で訂正後スナップショットを返す。検証失敗は `ResponseStatusException` を使い、`ApiErrorResponse(message)` 形式で返す。
- 判断理由: Entity を直接公開しない既存規約と、フロントエンドがエラーメッセージを表示できる既存の共通処理を維持するためである。
- 根拠: `CODEX.md`「API は Entity を直接返さず DTO」、`PendingOrderResponse.java`、`PositionExitOrderResponse.java`、`ApiExceptionHandler.java`。

### OCO の更新は全体を同一トランザクションで扱う

- 判断内容: 人間判断によって OCO の訂正を許可する場合、対象となるレッグの検証と保存は同じ口座ロック・トランザクション内で行い、一部だけ成功させない。
- 判断理由: 既存仕様は OCO をセットとして扱い、取消や片側約定時の相互取消もグループ全体で処理している。部分成功は OCO の意味を壊す。
- 根拠: `ADR-0009_OCOグループID方式と状態区別.md`、`TriggerOrderService.java` の `cancelOcoOrderLocked` と `cancelOcoSiblings`。

## 残存する未確定事項

### TP/SL の数量変更と部分決済

- 人間の判断が必要な内容: Issue の「TP/SL の数量変更」が部分決済注文を新設する意味か、IFD/IFO 親注文の数量変更に伴う子数量同期だけを意味するか。
- 判断が必要な理由: 現行 TP/SL は建玉全数量を自動設定し、発動時の `closePositionForLockedAccount` も建玉全体を決済する。Issue と既存実装に仕様差があり、部分決済は建玉・損益・証拠金・残存注文に波及するユーザー向け業務仕様である。
- 候補:
  - TP/SL の部分決済を新設し、数量は建玉数量以下とする。
  - TP/SL は全数量決済を維持し、数量変更は IFD/IFO の親子同期だけに限定する。
  - Issue の数量変更対象を通常予約注文だけに修正する。

### 訂正対象に `WAITING` を含めるか

- 人間の判断が必要な内容: `PENDING` だけを訂正可能とするか、親約定前の子注文等に使用される `WAITING` も含めるか。
- 判断が必要な理由: コード上は両状態が未発動・取消可能として扱われる一方、Trading 画面の待機注文パネルは ADR 上 `PENDING` のみを表示する。`WAITING` を編集可能にすると親子注文の操作性が変わる。
- 候補:
  - `PENDING` のみ。
  - `PENDING` と `WAITING` の両方。ただし `WAITING` は複合注文詳細から操作する。

### OCO の訂正単位

- 人間の判断が必要な内容: TP/SL の 2 本を常に一括訂正するか、価格だけは片側訂正を許可するか。

- 候補:

### IFD/IFO の親子訂正ルール
